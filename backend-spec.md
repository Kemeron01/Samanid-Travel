# Backend Spec: Tour Agency Platform

Технический список для бэкенд-разработчика: что делаем, из чего состоит, на что обратить внимание. Только выбранные фичи. Бизнес-контекст в `requirements.md`, описание для пользователя в `platform-overview.md`.

## 0. Стек и архитектура

- Python, Django, Django REST Framework, PostgreSQL, Redis, Celery (+ Celery Beat), Docker, CI
- Модульный монолит: каждое приложение Django отвечает за свою область, общение через сервисный слой и события, а не через прямые импорты моделей друг друга
- Слои внутри приложения: `models` → `services` (бизнес-логика, транзакции) → `api` (serializers, views). Логика во views не живёт
- Деньги: `DecimalField`, одна базовая валюта (допущено UZS), никаких float
- Время: UTC в БД, i18n и таймзоны на уровне представления
- Версионирование API: `/api/v1/`, документация OpenAPI (drf-spectacular)

## 1. Ядро

### 1.1. Аутентификация и безопасность (`accounts`)
**Что сделать**
- Регистрация/вход по email + пароль, вход через Google (OAuth2)
- JWT access + refresh с **ротацией refresh-токенов** (старый инвалидируется, повторное использование = отзыв всей цепочки)
- Список активных сессий, отзыв отдельной сессии/всех
- 2FA (TOTP) **обязательна** для ролей admin и manager
- Rate limiting на вход, регистрацию, применение промокодов, оплату
- Согласие на обработку персональных данных (версионируется), выгрузка и удаление данных клиента

**Модели:** `User`, `Session` (device, ip, last_seen, revoked_at), `RefreshTokenFamily`, `TOTPDevice`, `Consent`

**Внимание:** шифрование паспортных данных путешественников на уровне поля, доступ к ним логируется в `audit`.

### 1.2. RBAC (`accounts`)
- Роли: guest, customer, content_manager, manager, admin, guide (опционально)
- Права на уровне действий (`tour.edit`, `order.change_status`, `refund.create`...), роли это наборы прав
- Проверка прав в одном месте (permission classes), не в разбросанных `if`

### 1.3. Каталог (`catalog`)
**Что сделать**
- CRUD: Tour, Departure (для групповых), Addon, категории, направления
- Переводимые поля (i18n) на 2-3 языка: название, описание, программа
- Главная: сезонные подборки и праздники, информация о направлении; страница тур-пакетов
- Фильтры: цена, дата, направление, длительность, тип тура; простой поиск по названию
- Отзывы и рейтинги: только к завершённому оплаченному заказу, один на позицию, рейтинг тура агрегируется и кэшируется
- Вишлист: добавить/удалить, список

**Кэш:** Redis для списка туров и агрегатов рейтинга, инвалидация при изменениях.

### 1.4. Аудит-лог (`audit`)
- Кто, что, когда, до/после (diff) для админских и менеджерских действий и доступа к персональным данным
- Неизменяемая таблица, без soft delete

### 1.5. Общие требования
- Soft delete для бизнес-сущностей, миграции только через Django migrations
- Seed-данные для демо (management command)
- Health-check эндпоинт, структурированные логи (JSON)

## 2. Бронирование и места (`inventory`)

### 2.1. Hold и защита от овербукинга
**Что сделать**
- Резервирование мест внутри транзакции с блокировкой строк (`select_for_update`) на Departure или Seat
- `Reservation` (order, места, `expires_at`), по умолчанию 15 минут, настраиваемо
- Celery-задача освобождения просроченных hold + перевод заказа в `expired`
- Освобождение мест порождает событие для листа ожидания

**Обязательные тесты:** параллельные запросы (потоки/процессы) на последние N мест, результат: не больше N успешных броней. Нагрузочный сценарий «100 человек на 5 мест».

### 2.2. Seat map
- `Vehicle` + `SeatLayout` (схема: ряды, места, типы мест), `Seat` привязан к выезду/рейсу
- Блокировка каждого места отдельно, уникальность `(departure, seat)` на уровне БД
- Правила: места группы рядом (мягкая рекомендация), детское кресло только на допустимых местах

### 2.3. Ресурсы (гиды, транспорт)
- `Resource` (type: guide/vehicle), `ResourceAssignment` (resource, departure, time range)
- Запрет пересечений на уровне БД (`ExclusionConstraint` с `tstzrange` в PostgreSQL) и на уровне сервиса
- Назначение только менеджером; конфликт возвращает понятную ошибку

## 3. Ценообразование (`pricing`)

### 3.1. Расчёт цены
Порядок применения (детерминированный), результат сохраняется **снимком** в заказе:
1. базовая цена позиции
2. тариф по возрасту (взрослый/детский)
3. динамический коэффициент
4. допуслуги
5. промокод
6. списание бонусных баллов (с лимитом доли)
7. пени/доплаты

Единый сервис `PriceCalculator` возвращает разложение по строкам (для чека и отладки), а не только итог.

### 3.2. Динамическая цена
- Правила в БД, управляются из админки: пороги заполняемости, дни до выезда, коэффициенты
- История цен: каждое изменение коэффициента/цены хранится с датой
- Кэширование расчёта, но итог в заказе берётся из снимка

### 3.3. Промокоды
- Поля: код, срок, общий лимит, лимит на пользователя, минимальная сумма, привязка к туру/категории, тип (процент/сумма)
- Применение **атомарное** (счётчик через `F()` / блокировку), нельзя превысить лимит при параллельных заказах
- Возврат использования при отмене заказа

## 4. Трансферы (`transfers`)

- `Transfer` с упорядоченными точками (`origin`, `stops[]`, `destination`), дата/время, места, ребёнок, детское кресло, инструкции
- Интерфейс `DistanceProvider` (Distance Matrix API + мок для разработки и тестов)
- Расчёт: базовая ставка + км × тариф + время × тариф + надбавки, цена по сегментам
- Простая оптимизация порядка остановок (перебор/жадный алгоритм для небольшого числа точек), порядок можно зафиксировать клиентом
- Кэширование расстояний между парами точек

---

## 5. Заказы (`orders`)

### 5.1. Модель
`Order` → `OrderItem` (tour/departure, transfer, addon) → `Traveler` (на каждое место). Цена и условия хранятся снимком.

### 5.2. Статусная машина
```
draft → pending_payment → partially_paid → paid → confirmed → completed
          ↓                    ↓            ↓        ↓
       expired              cancelled   cancelled  cancelled → refunded
```
- Допустимые переходы заданы в одном месте, остальные отклоняются
- Каждый переход: запись в аудит + событие в outbox
- Для индивидуального тура: `awaiting_manager_confirmation` перед оплатой [ДОПУЩЕНИЕ]

### 5.3. Изменение оплаченного заказа
- Операции: смена даты выезда, смена/добавление/удаление пассажира, изменение допуслуг
- Алгоритм (сага): проверка доступности → hold новых мест → пересчёт цены → разница: доплата или частичный возврат → освобождение старых мест → перевыпуск ваучера
- Любой шаг может упасть: нужны компенсации, никаких «подвешенных» мест и денег

### 5.4. Отмена
- Политика: без штрафов, полный возврат [РЕШЕНО]; параметр `cancellation_deadline_days` (по умолчанию без ограничения) [ОТКРЫТО]
- При отмене: освобождение мест, возврат платежа, сторно проводок, возврат баллов и использования промокода, событие листу ожидания
- Срок возврата: `refund_days` (в настройках, значение утвердить)

---

## 6. Платежи (`payments`)

### 6.1. Провайдер и мок
- Интерфейс `PaymentProvider`: `create_payment`, `get_status`, `refund`, `verify_webhook`
- `MockPaymentProvider`: эмулирует платёж и асинхронный вебхук (Celery-задача с задержкой), возможность симулировать успех, отказ, повтор вебхука
- Реальные провайдеры (Payme/Click/Stripe) подключаются новыми адаптерами без изменения домена

### 6.2. Вебхуки и идемпотентность
- Таблица `WebhookEvent` с уникальным `provider_event_id`: повторный вебхук обрабатывается один раз
- Идемпотентные ключи при создании платежа и возврата
- Сверка (reconciliation) статуса платежа и заказа периодической задачей

### 6.3. Рассрочка
- `PaymentSchedule` (график): депозит подтверждает бронь, остальное по датам
- Напоминания, начисление пени по правилу из настроек, блокировка выезда и автоотмена при долге за N дней до выезда
- Все начисления и платежи отражаются в леджере

---

## 7. Финансовый леджер (`ledger`)

- Двойная запись: `LedgerAccount`, `LedgerEntry` (debit, credit, amount, order, reason), сумма дебетов = сумме кредитов в каждой транзакции
- Счета: расчёты с клиентами, денежные поступления, выручка, возвраты, скидки по промокодам, бонусные обязательства, пени
- Проводки **неизменяемы** (запрет update/delete на уровне БД/модели), исправления только сторно
- Баланс заказа и отчёты строятся из проводок
- Тесты: инвариант «сумма всех проводок = 0» после любой операции (оплата, возврат, изменение, рассрочка)

---

## 8. Outbox, саги, фоновые задачи (`events`)

### 8.1. Transactional Outbox
- Событие пишется в `OutboxEvent` **в той же транзакции**, что и изменение данных
- Диспетчер (Celery) читает необработанные события, доставляет подписчикам, помечает обработанными; при сбое ретраи с backoff, затем dead letter
- Обработчики идемпотентны

### 8.2. Саги
- Оформление заказа, изменение оплаченного заказа, отмена с возвратом
- Состояние саги хранится в БД, каждый шаг имеет компенсацию
- Тесты на падение каждого шага

### 8.3. Периодические задачи (Celery Beat)
- освобождение просроченных hold
- напоминания о платежах и выезде
- начисление пеней, проверка долгов по рассрочке
- сверка платежей
- обновление листа ожидания
- генерация ваучеров и манифестов (по событию)
- обновление агрегатов дашборда

---

## 9. Уведомления (`notifications`)

- Каналы: email, Telegram-бот [РЕШЕНО], SMS не делаем
- Общий интерфейс `NotificationChannel`, адаптеры email и Telegram
- Шаблоны с i18n; язык берётся из профиля пользователя
- Привязка Telegram: пользователь получает одноразовый код, отправляет боту, аккаунты связываются
- События: подтверждение заказа, ваучер, напоминание о платеже и выезде, отмена и срок возврата, освободилось место (лист ожидания), начислены баллы

---

## 10. Документы (`documents`)

- **Ваучер:** PDF с номером брони, составом, QR-кодом (содержит подписанный токен проверки), перевыпускается при изменении заказа
- **Манифест:** список пассажиров рейса (возраст, дети и кресла, пожелания, контакты, места по схеме), PDF, доступ менеджеру и закреплённому гиду
- Генерация асинхронная (Celery), файлы в хранилище (локально или S3-совместимое)

---

## 11. Лист ожидания (`waitlist`)

- `WaitlistEntry` (departure, user, места, created_at, статус)
- При освобождении мест: берётся первый в очереди, создаётся временный hold на него, уведомление, окно времени (настраиваемо)
- Не успел: hold снимается, предложение уходит следующему
- Тесты на гонки: два освобождения одновременно, пользователь бронирует мимо очереди

---

## 12. Лояльность (`loyalty`)

- Реферальный код у каждого клиента, привязка приглашённого при регистрации
- Баллы начисляются **после оплаты первого заказа** приглашённого, обоим сторонам
- Бонусный счёт ведётся через леджер (баллы это обязательство); срок жизни и лимит списания в настройках [ОТКРЫТО]
- Защита от самореферала и дублей аккаунтов (связка с антифродом)

---

## 13. Антифрод (`fraud`)

- Правила: лимиты попыток применения промокодов, массовые регистрации (IP/устройство), дубли заказов, подозрительные платежи (много неудач подряд, необычные суммы)
- Решения: allow / review / block, всё пишется в аудит
- Правила настраиваются в админке (пороги), без деплоя

---

## 14. Админка и аналитика (`analytics`)

- Django Admin или кастомная админка поверх API; доступ по RBAC, 2FA для admin/manager
- Управление: туры, выезды, цены, правила динамической цены, допуслуги, промокоды, ресурсы, роли
- Заказы: фильтры, ручная смена статусов (только допустимые переходы), ручной возврат
- Дашборд: выручка, заполняемость выездов, топ-направления, воронка заказов (создан → оплачен → отменён)
- Агрегаты считаются фоновыми задачами и кэшируются
- Экспорт отчётов в CSV/Excel (асинхронно для больших выборок)

---

## 15. Наблюдаемость и эксплуатация

- Метрики (Prometheus): число заказов, платежей, ошибок, размер очереди outbox, время ответа
- Трейсинг (OpenTelemetry) через API → Celery → провайдеры
- Дашборд Grafana и алерты на сбои платежей, рост dead letter, рост hold-ов без оплаты
- Мониторинг ошибок (Sentry), health-check
- Автобэкапы БД, Docker Compose для запуска, CI (линтер, тесты, миграции)

---

## 16. Что НЕ делаем

Маркетплейс и партнёрские API, групповые заказы с раздельной оплатой, полнотекстовый поиск, тикеты поддержки, мультивалютность, SMS, реальные платёжные провайдеры, оптимистичные блокировки в админке как отдельная фича.

## 17. Порядок реализации

1. **Фундамент:** проект, Docker, CI, `accounts` (регистрация, JWT, RBAC), `audit`
2. **Каталог:** `catalog` + админка, i18n, фильтры, кэш
3. **Заказы:** модели, статусная машина
4. **Места:** `inventory`, hold, seat map, защита от гонок + нагрузочный тест
5. **Оплата:** `payments` с моком, вебхуки, идемпотентность
6. **Леджер:** проводки на каждое движение денег
7. **События:** outbox, Celery, `notifications` (email, Telegram)
8. **Цены:** `pricing`, динамика, промокоды, `fraud`
9. **Трансферы:** маршруты, расчёт по остановкам
10. **Сложные потоки:** рассрочка, изменение заказа, отмена, лист ожидания (на сагах)
11. **Операции:** ресурсы, ваучер, манифест
12. **Рост:** `loyalty`, отзывы, вишлист
13. **Завершение:** усиленная аутентификация (2FA, Google, сессии), дашборд и экспорт, наблюдаемость

## 18. Определение «готово» для каждой фичи

- Бизнес-логика в сервисном слое, покрыта тестами (включая негативные и конкурентные сценарии)
- Эндпоинты описаны в OpenAPI, права проверяются через RBAC
- Значимые действия пишут аудит и события
- Операции с деньгами идемпотентны и отражены в леджере
- Миграции применяются на пустой и на заполненной БД
